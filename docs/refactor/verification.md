# Проверка реестра модулей

`module-contracts.md` описывает контракты модулей. `module-registry.json` перечисляет исходные файлы и связывает их с решением и доказательствами. Наличие файла в реестре не означает, что его поведение уже зафиксировано тестами.

## Команды

- `node docs/scripts/check-refactor-inventory.mjs` проверяет полноту реестра относительно существующих отслеживаемых и неигнорируемых новых исходников.
- `node docs/scripts/check-refactor-inventory.mjs --sync` явно обновляет список файлов. Новые записи получают `pending`; удаления требуют просмотра Git diff. Команда не принимает поведение автоматически.
- `node docs/scripts/check-refactor-inventory.mjs --require-accepted` дополнительно требует решение и непустой список доказательств для каждой записи. Пока остались `pending`, ожидается ненулевой код завершения.
- `node --test docs/scripts/check-refactor-inventory.test.mjs` выполняет самопроверки инструмента на временных Git-репозиториях; временные каталоги удаляются.

Исполняемые проверки запускаются последовательно через `docs/scripts/run_limited_check_windows.py`: Windows Job Object, один логический CPU, ограничение памяти и таймаут. Скрипты реестра используют стандартную библиотеку Node.js и Git; они не импортируют приложение, не читают dotenv и не обращаются к API или базе данных.

## Проверенный результат

Пять самопроверок успешно выполнены с Node.js 24.20.0 в Windows Job Object с лимитом 1024 MiB, одним CPU и таймаутом 90 секунд. Проверены появление и удаление исходников, дубли, повреждённые метаданные, запрет автоматической приёмки через `--sync`, обязательность решения и доказательств.

Это проверка инструмента, а не фиксация поведения всех модулей сайта и сервисов. Остальные записи остаются `pending` до своих gates. Перед запуском браузерных и DB-harness требуется проверка границ W0; её результаты приведены ниже.

## W0: безопасные границы проверочных стендов

Production-код приложения, API и сервисов этим этапом не изменён. Изменены только тесты и QA-инструменты.

| Контракт | Выполненная проверка | Результат |
| --- | --- | --- |
| Опасный DB target отвергается до подключения; capability привязана к временному кластеру | `python -B web/tests/test_qa_safety.py` | 3 проверки прошли |
| Точные QA origins, запрет API proxy в mock-режиме, HTTP redirects и WebSockets; безопасные пути и новые внешние каталоги | `node --test frontend/scripts/qa-safety.test.mjs` | 6 тестов прошли |
| Изменённый conftest совместим с чистыми quota/protocol-проверками | `python -I -B docs/scripts/run_subscription_unit_checks.py` | 7 проверок прошли |
| Harness выдаёт capability только своему готовому кластеру; миграции и выбранные DB-контракты проходят | `python -I -B docs/scripts/run_postgres_subscription_checks.py --python <изолированный-python>` | PostgreSQL 18.6: 33 теста прошли, 1 предупреждение; сервер остановлен, временный кластер удалён |
| Сбор crash/support-тестов без DB capability, dotenv, исходящих соединений и DNS | `python -I -B docs/scripts/run_guarded_web_collection.py` | Репозиторный коллектор собрал 41 тест; попыток подключения и DNS не было. Внешний прототип дал тот же результат |

Все перечисленные исполняемые проверки выполнены последовательно в Windows Job Object с одним CPU. Лимит для standalone guards и collection — 1024 MiB; для PostgreSQL — 4096 MiB. Предупреждение PostgreSQL-прогона относится к короткому фиктивному HMAC-ключу теста, а не к production-ключу.

Две регрессии QA-границ воспроизведены до исправления: существующий output legacy-runner допускался до вызова запуска браузера; внешний dependency-репозиторий не защищался от выбора каталогом вывода. После исправлений текущие 6 Node-тестов прошли. В отрицательном тесте запуск браузера заменён запретом, а запись вне выбранного временного каталога запрещена: реальный браузер не запускался.

В рамках W0 синхронизированный реестр содержал 411 исходников: 9 инфраструктурных записей имеют ограниченное доказательство `retain`, 402 остаются `pending`. Проверка полноты прошла; `--require-accepted` ожидаемо завершилась с кодом 1. Это не приёмка поведения оставшихся модулей.

Эти результаты не означают прохождение полного crash/support HTTP-набора, одобренных auth/release-гонок или визуальной приёмки. DB-проверки используют только выделенный loopback-кластер с capability; произвольный `TEST_DATABASE_URL` недопустим. Исторические QA-отчёты и изображения не перезаписываются.

## W2 / D17: одноразовые токены

Добавлен `web/tests/test_auth_token_concurrency.py`: 10 обычных контрактов трёх вариантов токена и 3 двухсоединительные регрессии. Выполнен прежний набор из 33 DB-тестов вместе с новыми 13, без изменения самих регрессионных assertions между красным и зелёным прогонами.

- Guarded collection без DB capability: 54 теста, 0 попыток DNS и подключения; `C:/Temp/watchdemo-w2-auth-offline-collection.log`.
- До исправления: 43 passed / 3 failed, 32.74 s. Каждая гонка дошла до `D17 duplicate consumption: ['committed', 'committed']` после подтверждения разных PostgreSQL PID и двух реальных чтений; `C:/Temp/watchdemo-w2-auth-postgres-red.log`.
- После согласованного D17-исправления: 46 passed / 0 skipped, 31.37 s; `C:/Temp/watchdemo-w2-auth-postgres-green.log`. Проверка активности и отсутствия `used_at` добавлена в существующий `SELECT ... FOR UPDATE`; проигравший получает прежнюю ошибку недействительного токена. Обычные ошибки и rollback проверены тем же набором.
- Прогоны последовательные: Windows Job, один CPU, 4096 MiB / 300 s для PostgreSQL, 1024 MiB / 90 s для collection. Оба собственных кластера PostgreSQL 18.6 остановлены и удалены. Предупреждение о коротком фиктивном ключе сохранено. Времена не являются сравнением производительности.

Оба независимых post-fix ревью шести файлов прошли без находок; это статические проверки исходников и журналов, не повторное исполнение. В отдельном семифайловом acceptance-worktree реестр полон: 412 исходников, 10 ограниченных `retain`, 402 `pending`; пять самопроверок реестра прошли. Несохранённые W1-файлы в этот артефакт не включены.

Ограничения, точный сценарий и статус независимых ревью: [backend-auth-qa.md](backend-auth-qa.md). Это не полный контракт HTTP/JWT/refresh/всего auth-модуля. Результаты D18 приведены ниже; полная визуальная и native-приёмка остаются открытыми.

## W2 / D18: конкурентная публикация релизов

Добавлен `web/tests/test_release_publication.py`: 8 обычных контрактов и 3 двухсоединительные регрессии с реальными `ReleaseService`, репозиторием, миграциями, транзакциями и файлами в собственном временном каталоге.

- Guarded collection: 65 тестов, 0 попыток DNS и подключения, без DB capability; `C:/Temp/watchdemo-d18-offline-collection-bounded-ids.log`.
- Чистый красный прогон: 54 passed / 3 failed, 37.07 s, без ошибок стенда. Все три случая подтвердили перезапись либо удаление файла уже закоммиченного победителя после проверки разных PID/транзакций, реальных чтений и точной причины отказа проигравшего; `C:/Temp/watchdemo-d18-postgres-meaningful-red.log`.
- Исправление в рамках D18: собственный staging-каталог на той же файловой системе, реальный уникальный INSERT/flush до атомарной замены публичного файла. URL, метаданные, валидация, обычные ошибки и характеризованный precommit-orphan сохранены.
- Финальный зелёный прогон, включая проверку отсутствия неожиданных файлов: 57 passed / 0 skipped, 38.37 s; `C:/Temp/watchdemo-d18-postgres-final-green.log`. Это прежние 46 DB-тестов и новые 11. Существующее предупреждение о фиктивном HMAC-ключе сохранено.
- Прогоны последовательные: Windows Job, один CPU, 4096 MiB / 300 s для PostgreSQL и 1024 MiB / 90 s для collection. PostgreSQL 18.6 остановлен, временные кластеры удалены. Времена не доказывают ускорение.

Первый прогон отдельно выявил слишком длинный автоматический pytest ID для синтетического файла >1 MiB в Windows. Короткие явные ID исправили только метаданные теста; ошибки стенда не засчитаны как подтверждение D18.

Оба initial-ревью четырёх файлов и оба независимых post-fix ревью шести файлов прошли без находок. Это статический разбор исходников и журналов, а не независимое повторное исполнение или проверка хешей; реестр и staging остаются ответственностью основного агента. Точные сценарии, ограничения HTTP/COMMIT/cross-platform и команды: [backend-release-qa.md](backend-release-qa.md). Это не приёмка всего release-модуля.

## Границы доказательств

Решение в реестре относится к указанному контракту и проверке, а не к произвольным будущим изменениям файла. При изменении исходника требуется заново выполнить соответствующие проверки и пересмотреть доказательства. Реестр проверяет структуру записей, а не истинность произвольного текста в поле `evidence`.

Визуальные эталоны, проверка полного homepage и оставшиеся одобренные гонки выполняются отдельными этапами. Успешный статический check не заменяет браузерную проверку, а эмуляция устройства не подтверждает плавность на физическом телефоне.
