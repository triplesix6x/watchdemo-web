## Обязательные уточнения после перезапуска

D25 из спеки имеет приоритет: агенты только читают и редактируют. Они НЕ запускают тесты, сборки, Docker, БД, браузеры, установку зависимостей и dev-серверы. Проверки выполняет только координатор, последовательно, с техническими лимитами памяти/CPU. Прежние окружение и worktree в `/tmp` утрачены; упоминание подготовленного Python ниже — историческое, а не доступный ресурс. Новые worktree находятся в `/home/bigboss/.cache/watchdemo-prelaunch-worktrees/`.

Общие wire-конвенции: `published_at`, `release.effective_at`, `document.effective_at` — строгие даты `YYYY-MM-DD` (effective допускает null); активация не раньше соответствующей UTC calendar date, фактический timestamp отдельно UTC. `catalog_sha256` — SHA256 от `json.dumps(payload_without_catalog_sha256, ensure_ascii=False, sort_keys=True, separators=(',', ':')).encode('utf-8')`, без завершающего LF во входе хеша. Текстовый artifact допускает pretty-print + LF.

Тарифная часть D13 уточнена в `docs/SPEC-subscription-sync.md`. Тарифный API сохраняет `id`, `min_tier`, `allowed`, `monthly_limit` и `limit_period: 'calendar_month' | 'activation_month' | null`. `monthly_limit` относится к новым импортам и созданиям собственных наборов на весь аккаунт: Free 5/1, Plus 15/2, Pro без лимита. `limit: number | null` относится к одновременно существующим группам: 2/5/без лимита. Период Free календарный UTC, платный месяц отсчитывается от исходной активации непрерывного платного доступа. Общий scope аккаунта включает все компьютеры. У тарифа `price_rub: number`, `sales_open: false`. Feature IDs: `demo_import`, `content_search`, `replay2d`, `advanced_stats`, `demo_groups`, `custom_sets`, `voice`, `notes`, `playbooks`. Серверный учёт и проверки Windows реализуются совместно по новой спеке; этот документ не подтверждает завершение их проверки.

## Архитектурное основание

Frontend — React/Vite с публичным SSR/prerender и RU/EN маршрутизацией. Backend — FastAPI/PostgreSQL, регистрация создаёт пользователя и Basic. Почта — RabbitMQ и отдельный Resend consumer. Каждый контейнер собирается из своего каталога, поэтому runtime-чтение соседнего `docs/` недопустимо. Существующий periodic имеет advisory lock. Каталог документов, активация и доказательства — ответственность backend; рендер текста и статические адреса — frontend; доставка — mail. Регистрация не должна публиковать подтверждение почты до commit созданного аккаунта и принятия.

Рассмотрены API-only и генерируемые снимки одного источника. Выбран второй вариант: автономный SSR без сетевой зависимости сборки. Два generated-файла — производные, не два редактируемых источника. Добавляем проверку свежести. За основу выбран второй архитектурный кандидат (B), из первого (A) взяты атомарность активации/outbox, общий lock регистрации/активации и монотонный выпуск с запретом отката DB-policy старым контейнером. Независимый cross-judge оценил оба варианта 21/25 и предпочёл B после этих исправлений. Готовность публикации проверяется manifest, но это ограниченный сигнал, не гарантия состояния всех CDN-реплик; статические страницы публикуются первыми и старые адреса сохраняются. Не добавляем CMS, универсальный consent framework и внутренний протокол claim/finish между mail и web. Остаточный риск фактической доставки нельзя называть exactly-once.

Не трогать исходные пользовательские HTML/ZIP. Не коммитить копии спеки из worktree. Не развёртывать, не выполнять реальные регистрации/письма/платежи. Обычный Vite dev проксирует production; QA только mock или изолированный localhost.

## Единый каталог

Источник: `docs/legal/catalog.json`, `docs/legal/fields.json`, `docs/legal/texts/<id>/<revision>.txt`. Публикуем только `terms`, `offer`, `privacy`, `cookies`, `details` из заготовок 02/03/04/05/07. Файлы внутренних инструкций и отдельное Resend-согласие не публикуются. Юридические изменения остаются явно отмеченными черновыми изменениями, правовое основание не выдумываем.

Генератор stdlib: `python docs/scripts/build_legal_catalog.py`, проверка без записи: та же команда с `--check`. Вывод:

- `frontend/src/content/legal.generated.json`;
- `web/APP/legal_catalog.generated.json` — тот же JSON;
- `frontend/public/legal/catalog-manifest.json` — только безопасные метаданные готовности публикации.

Форма generated-каталога (ключи snake_case):

```json
{
  "schema_version": 1,
  "catalog_sha256": "sha256 deterministic canonical payload without this key",
  "release": {
    "sequence": 0,
    "effective_at": null,
    "legal_review_approved": false,
    "evidence_retention_days": null
  },
  "documents": [{
    "id": "terms",
    "revision": "2026-11-03-draft-1",
    "status": "draft",
    "language": "ru",
    "title": "Условия использования сайта и программы WatchDemo",
    "published_at": "2026-11-03",
    "effective_at": null,
    "body": "UTF-8 text with LF",
    "sha256": "sha256 of exact UTF-8 body bytes",
    "url": "/legal/terms/2026-11-03-draft-1"
  }]
}
```

В источнике вместо `body` — `body_file`; `sha256`, `url`, `catalog_sha256` вычисляются. Разрешены статусы `draft`, `effective`, `archived`; максимум одна effective-редакция на id. Английская оболочка не является переводом юридического оригинала. TXT скачивается в точности из `body`, печать убирает chrome сайта. Локальные файлы внутри каталога, без traversal/HTML исполнения/сети. Известные технические поля заполняются по фактам, неизвестные `[[...]]` сохраняются. Никаких вымышленных реквизитов.

`catalog-manifest.json`: `{schema_version:1,catalog_sha256:"...",release_sequence:0,documents:[{id,revision,sha256,url}]}`. Список выводится из того же каталога и используется prerender для реальных страниц; не вести второй ручной список. TXT скачивается из точных body-байтов на странице, наличие отдельного TXT URL не требуется. При действующем выпуске backend проверяет совпадение manifest на единственном настроенном frontend origin, с timeout, без cross-origin redirect. Проверка не делается для полностью чернового каталога и не вызывает сеть в тестах без явного fake. До совпадения новые требования и рассылка НЕ активируются. Для регистрации после появления effective в локальном bundle, но до подтверждённой активации, безопасный отказ вместо обхода нового требования.

Опубликованные редакции сохраняются, изменение уже действовавшего id+revision под другим хешем отвергается backend. Нужна новая редакция. Положительная sequence монотонна; старый процесс не понижает действующую policy. В БД сохраняются highest sequence и fingerprint: равная sequence с другим fingerprint отвергается, возврат старого текста требует большей sequence. Изменение черновиков не является новым действующим выпуском и не меняет fingerprint уже применённого active-выпуска. Активация требует непротиворечивой effective-даты, юридического утверждения, срока хранения, отсутствия пропусков во всех включаемых документах и необходимых сопутствующих документов. Offer остаётся draft, продажи всегда выключены. Срок хранения не придумываем и не включаем active в поставляемых файлах.

## Signup API

`GET /api/v1/legal/signup-policy`:

```json
{
  "mode": "draft",
  "policy_id": null,
  "catalog_sha256": "...",
  "required_terms": null,
  "privacy_url": "/legal/privacy/2026-11-03-draft-1"
}
```

В enforced-режиме `policy_id` — серверный идентификатор активного выпуска, `required_terms`: `{document_id:"terms",revision:"...",sha256:"...",url:"/legal/terms/..."}`. Backend владеет обязательностью, frontend не определяет её только своим bundle. Несовпадение версии/хеша отображаем как требование обновить страницу/условия, без подмены текста.

Дополнение существующей регистрации:

```json
{"legal_acceptance":{"policy_id":"...","terms_revision":"...","terms_sha256":"...","accepted":true}}
```

Поля существующего запроса сохраняются. В draft-режиме галочки принятия нет, регистрация без нового поля работает; предоставленное принятие черновика не создаёт доказательство и отклоняется понятной ошибкой. В enforced-режиме требуется точное принятие активных terms; отсутствие/false — 422, устаревшая policy/хеш — 409. Сервер не принимает дату, IP и user_id от клиента. Locale — существующий язык аккаунта/формы. Policy ПД — уведомление и ссылка, а не универсальное согласие. Никаких обязательных Resend, аналитических или возрастных галочек.

Пользователь и запись принятия создаются одной транзакцией. Проверка policy и создание аккаунта/принятия удерживают общий с активацией DB lock до commit; это исключает гонку чтения старой policy с одновременной активацией. Append-only учёт: аккаунт, серверное UTC время, document_id/revision/sha256, действие `accept_terms`, locale, IP, ограниченный User-Agent. IP только от доверенных proxy; текущий `trusted_hosts=["*"]` устранить, конфигурацию прокси описать. Нельзя потерять доказательство из-за обычного удаления аккаунта, сроки и необходимые операции удаления — согласно согласованной политике, не бессрочное обещание.

## Активация и сервисные письма

Backend сохраняет неизменяемые снимки effective-редакций, активный выпуск, принятия и outbox. Под DB advisory lock атомарно создаёт активацию/cutoff и задания только существующим активным подтверждённым аккаунтам. Логическая уникальность на account+document_id+revision; новый аккаунт после cutoff не получает письмо об изменении принятой при регистрации редакции. Перезапуск, параллельные workers и правка draft не создают повторные задания. Удалённые/деактивированные адресаты подавляются перед постановкой. Существующие входы/Windows-доступ не блокируются и принятие задним числом не создаётся.

Periodic публикует pending outbox через существующий MQPublisher с broker confirm. Публикация не равна доставке, pending не теряется при падении. Для уведомления используем тип `legal_revision_updated`, обязательный стабильный `notification_id`, `created_at` (UTC ISO timestamp), `to_email`, `to_name`, `locale`, `data`:

```json
{
  "type":"legal_revision_updated",
  "notification_id":"uuid",
  "created_at":"2026-11-03T00:00:00+00:00",
  "to_email":"qa@example.invalid",
  "to_name":"QA",
  "locale":"ru",
  "data":{
    "document_title":"Условия использования",
    "document_revision":"revision",
    "effective_date":"date",
    "document_url":"https://configured-origin/legal/terms/revision"
  }
}
```

Оболочка старых типов совместима: новые поля optional для старых писем, но обязательны для нового типа. Backend формирует locale-путь `/en/legal/...` для EN оболочки; тело документа всё равно русское. Payload не содержит IP/UA, реквизитов-заготовок или рекламных блоков.

Mail проверяет новые поля, рендерит RU/EN subject+HTML+text и передаёт Resend2.29.0 `SendOptions.idempotency_key`, производный от notification_id. Поддержка параметра подтверждена установленным SDK. Не обещаем бесконечную provider-idempotency. Для нового типа нужны ограниченный срок повторов и прекращение/видимая ошибка при неизвестном исходе за пределами окна; нельзя бесконечно requeue одно уведомление. Компактное долговечное владение повторами: mail объявляет отдельные durable retry/failed очереди (без изменения аргументов уже существующей email очереди), retry очередь с фиксированной задержкой и dead-letter обратно в email, счётчик попыток и исходный created_at переносятся в сообщении/заголовках. После лимита/истечения срока/неисправимого payload сообщение оказывается в durable failed очереди с причиной, не получает новый notification_id. Backend различает pending/published, но не выдаёт published за sent. Максимум повторов и срок фиксируются в коде/тестах/runbook, срок выбирается консервативно внутри подтверждённого provider-window; если окно не подтверждено, не делать неоправданных гарантий. Не вводить скрытую бесконечную задержку и не терять финальную ошибку только в логах. Не переделывать все старые mail-flows без необходимости. Раскрыть пределы dedupe в runbook. Полный протокол внутренних claim/finish API здесь не нужен.

Все реально используемые типы сервисных писем проходят аудит шаблонов: подтверждение почты, восстановление, welcome если вызывается, смена почты/пароля, обновление документов. Ссылки/данные экранируются, одноразовые токены не логируются. Реальное отключение open/click tracking зависит от возможностей Resend и конфигурации домена; не придумывать несуществующие API-параметры и не объявлять dashboard-настройку проверенной.

## Frontend и тексты

`/legal`, `/legal/:id`, `/legal/:id/:revision` и `/en/...`: общий раздел, последняя доступная редакция и неизменяемый адрес редакции. У всех пяти документов заметный draft-статус; тексты не оформляются как уже действующие. Черновики noindex, отдельно исключаются из sitemap, но prerender обязательный и прямые адреса работают. EN — перевод навигации/предупреждений, русский оригинал. Из форм новые вкладки без потери состояния. Печать и TXT без server-PDF.

Footer на public/auth/account страницах: документы/условия/политика/cookies/реквизиты и «Настройки cookies». Небольшое уведомление на первом визите, «Понятно» и «Настройки», localStorage только для закрытия; доступ к сайту не блокируется. Диалог settings с необходимыми хранилищами и честным сообщением, что аналитика ещё не подключена; несуществующее согласие не создаётся, будущая аналитика по умолчанию заблокирована. Использовать существующий Dialog/focus trap, keyboard/focus restore, мобильный viewport и tokens. Не менять hero/GhostFibers.

Обновить сайт+API на Free/Plus/Pro, id basic/plus/pro совместимы. D13 — источник матрицы; применение Windows-квот НЕ здесь. Страница тарифов, account access и маркетинговые CTA не должны обещать действующую покупку: «Продажи пока не открыты», бесплатный тест через существующую поддержку, без нового guest form. Статья FAQ — запросы сведений/исправления/удаления через поддержку. В поддержке предупреждение не присылать демки, голоса, пароли, платёжные секреты и данные третьих лиц.
