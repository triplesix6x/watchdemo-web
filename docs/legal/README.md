# Каталог юридического предзапуска

Все пять поставляемых документов — **«Черновик, не действует»**, revision `2026-11-03-draft-1`, дата публикации `2026-11-03`. Release sequence `0`, effective_at `null`, legal_review_approved `false`, evidence_retention_days `null`. Принимать черновики нельзя. Продажи закрыты; оферта всегда draft в рамках этого этапа.

## Источник и границы

Редактируемые источники: `docs/legal/catalog.json`, `docs/legal/fields.json`, `docs/legal/texts/<id>/<revision>.txt`. Исходные публичные заготовки архива: 02 → terms, 03 → offer, 04 → privacy, 05 → cookies, 07 → details. Исходный словарь 01 сохранён с заполнением подтверждённых технических полей и добавлением явно неизвестных полей. Архивные пользовательские файлы не изменялись. Внутренние инструкции, отдельное согласие Resend, отдельное согласие аналитики и тарифное приложение архива не публикуются. Существенные адаптации перечислены ниже; это черновые, не юридически утверждённые изменения.

Генератор — stdlib Python 3.10+; зависимостей, сети, базы данных, frontend/backend импортов и выполнения текста нет. Выдаваемая схема строго соответствует `docs/LEGAL-implementation-contract.md`; отдельный `sales_open` в каталог не добавляется. Закрытые продажи обеспечиваются запретом любых не-draft редакций offer; флаг тарифного API принадлежит backend.

Выходные файлы (не редактировать вручную):

- `frontend/src/content/legal.generated.json`;
- `web/APP/legal_catalog.generated.json` — побайтово тот же JSON;
- `frontend/public/legal/catalog-manifest.json` — только schema_version, catalog_sha256, release_sequence, документы с id/revision/sha256/url, без body и полей оператора.

Список страниц берётся из generated-каталога/manifest, а не из второго ручного списка. Публичный каталог содержит только пять разрешённых id. Текст должен выводиться как текст, не исполняемый HTML; английская оболочка не переводит русский оригинал. TXT скачивается из точных UTF-8 body-байтов. Страницы черновиков требуют заметной маркировки, noindex и исключения из sitemap со стороны frontend.

## Генерация и проверка (только координатор)

По D25 реализационный агент **не запускает даже unit-тесты или генератор**. Следующие команды предназначены координатору, последовательно, с согласованным техническим ограничением ресурсов, из корня соответствующего worktree/репозитория:

```sh
python3 docs/scripts/build_legal_catalog.py
python3 docs/scripts/build_legal_catalog.py --check
python3 -m unittest discover -s docs/scripts/tests -p 'test_build_legal_catalog.py' -v
```

Первой генерацией координатор создаёт три отсутствующих артефакта. После интеграции повторить генерацию и `--check` в объединённом дереве. Не применять боевой `.env`; этим командам он не нужен. Тесты используют только временные fixture-файлы и не запускают инфраструктуру. Результат команд должен быть сообщён отдельно: наличие этого runbook не означает их выполнения.

`--check` сначала валидирует источники и локальную неизменяемость, затем побайтово сравнивает все три файла. При отсутствии/рассинхроне возвращает exit 1. **Ничего не пишет, не исправляет и не создаёт каталоги**, даже при ошибке. Обычная генерация валидирует весь источник и существующие снимки до записи любого выхода. При внешнем прерывании между тремя записями возможен частичный набор; повторить генерацию, затем `--check`. Это не транзакция публикации.

## Даты, подстановки и точные хеши

`published_at`, `document.effective_at`, `release.effective_at` — только реальные даты `YYYY-MM-DD`, не timestamp; draft effective_at только null. Дата действия не раньше публикации. У всех четырёх effective-компаньонов одна дата, равная release.effective_at. Будущая дата допустима в артефакте, но **backend не активирует выпуск раньше этой календарной даты UTC**; дата без времени не трактуется как локальная полночь. Timestamp фактической активации/принятия сохраняется отдельно в UTC. Генератор не активирует policy и не отправляет уведомления.

Текст декодируется из UTF-8, CRLF/CR нормализуются в LF, BOM и NUL запрещены; пробелы и завершающий LF не добавляются и не обрезаются. Затем выполняется **один проход** подстановок `[[FIELD]]` из fields.json. Пустое/неизвестное поле остаётся видимым `[[FIELD]]`; вставленный текст повторно не интерполируется. Поэтому вложенные неизвестные поля в техническом инвентаре также остаются видимыми. VERSION, DATE, YEAR всегда берутся из метаданных конкретной редакции, EFFECTIVE_DATE — из её даты действия; для draft остаётся незаполненным независимо от общего словаря. Это не юридическая дата «сегодня» и не версия генератора.

`document.sha256 = hashlib.sha256(body.encode('utf-8')).hexdigest()` — хеш **точных выдаваемых body-байтов**, не TXT-шаблона и не pretty JSON.

`catalog_sha256 = hashlib.sha256(json.dumps(payload_without_catalog_sha256, ensure_ascii=False, sort_keys=True, separators=(',', ':')).encode('utf-8')).hexdigest()` — без LF во входе хеша. Documents стабильно упорядочены по `(id, published_at, revision)`. Выходной JSON pretty-print, sorted keys, завершающий LF; это не вход хеша каталога. Manifest получает тот же catalog_sha256 и document.sha256, но сам не является входом хеша каталога. Не вычислять хеш из распечатанного JSON или отредактированной копии текста.

## Переход к действующей редакции — не выполнять при разработке

1. Юрист заполняет и проверяет оператора/контакты, возрастную формулировку, основания обработки, сроки, Resend и трансграничную передачу. Технический ответственный подтверждает инфраструктуру, полный состав хранилищ и настройки почты. Новое вымышленное основание/адрес/срок не подставлять.
2. Сохранить старые файлы и записи catalog. Для юридического изменения создать новый id+revision, новый TXT и метаданные. У прежней действующей редакции меняется только status → archived, не текст, заголовок, даты, язык или URL. Общие fields могут менять хеши старых шаблонов: для сохранённой редакции зафиксировать уже опубликованный body в TXT без динамических полей либо оставить значения неизменными. Никогда не удалять опубликованные старые адреса. Текущий draft допускает доработку до утверждения, но старые редакции не удаляются из каталога.
3. Все четыре документа terms/privacy/cookies/details новой policy должны быть effective с общей effective_at. Offer остаётся draft. Никаких `[[...]]` в заголовках/текстах effective или archived. У каждого id максимум одна effective. Release sequence — положительная и выше прежней, legal_review_approved true, evidence_retention_days — согласованное положительное целое (fixture-значения тестов не являются рекомендацией срока).
4. Только координатор генерирует артефакты и выполняет проверки. Существующие generated-снимки проверяются по catalog/body hash; запрещены удаление прошлых редакций и изменение хеша/метаданных исторического effective/archived id+revision, в том числе через общий fields. Не удалять снимок ради обхода ошибки. На чистой сборке истории снимка может не быть: неизменяемость и монотонность дополнительно обеспечиваются постоянной историей backend. Генератор не заменяет DB-проверки равной sequence с иным fingerprint/запрет отката.
5. Публиковать статические страницы и manifest **раньше** backend policy. Сохранить старые страницы. Backend проверяет manifest на единственном настроенном frontend origin без cross-origin redirects и с timeout; совпадение — ограниченный сигнал, не гарантия готовности всех CDN-реплик.
6. Backend выполняет активацию только после UTC-даты, проверки manifest, юридического утверждения, срока, всех компаньонов, отсутствия пропусков и монотонности. До этого требования/рассылка не активируются; при локальном effective до подтверждённой policy регистрация безопасно отказывает. Draft-изменения не запускают уведомления.
7. Уведомления существующим подтверждённым активным аккаунтам — неблокирующие сервисные письма через durable outbox; без повторного обязательного принятия/записей задним числом. Реальные письма, платежи и production-активация в ходе разработки запрещены. Ограничения доставки и повторы документирует mail-lane, не генератор.

### Что подтверждено чтением текущего кода, а не production-проверкой

- `frontend/src/api/client.ts`: access token только в памяти, refresh через cookie, очистка cookie сервером; development mock localStorage не производственная аналитика.
- `web/API/views/auth/views.py`: cookie `rt`, HttpOnly, SameSite=Lax, Path `/api/v1/auth`, max-age из конфигурации, Secure из настройки; выход удаляет cookie. Вход получает User-Agent и IP через серверный client_ip.
- `web/APP/config.py`: defaults refresh TTL 30 дней, max session age 365 дней, email token 24 часа; эти значения переопределяются конфигурацией, боевое окружение не читалось.
- `web/APP/services/auth_service.py`: email verification, password reset/change, email change; обычное удаление обезличивает пользователя и удаляет сеансы/подписку/одноразовые токены, не всю строку и не аудит.
- `web/SPI/db_adapter/models/support.py`, `web/APP/services/support_service.py`: отдельные web/Telegram контакты, идентификаторы и сообщения, изображения, временные/служебные данные; размещение хостов этим не подтверждается.
- `frontend/src/config.ts`: существующий `SUPPORT_BOT_URL`, не новый придуманный контакт.
- `mail/email_service.py`: Resend получает from/to/subject/html/text; код не подтверждает отключение open/click tracking или размещение/срок хранения у провайдера.

Frontend/backend/mail меняются параллельно в других деревьях: перед будущей активацией этот read-only инвентарь сверить с объединённым diff. В этой lane business-код не меняется. Поставляемые источники заведомо НЕ готовы к действующему выпуску, что является требованием предзапуска, а не обходом валидации.
