## Объединение истории миграций

При продолжении три апрельские миграции находились в рабочем дереве как untracked. Они образовывали отдельную цепочку, а майская baseline повторно создавала те же таблицы. Общий backend-набор падал с `Multiple head revisions are present`. До исправления новый graph-тест показал `Left contains one more item: 'a1b2c3d4e5f6'`.

После прямого текстового разрешения пользователя история стала линейной:

```text
c5495913782c -> 9c6ff58f0373 -> a1b2c3d4e5f6 -> 907b2d179318
-> 2719b4ef61f3 -> 03b05dc2017c -> 0002_locale_changelog
-> 0003_crash_reports -> 0004_support -> 0005_legal_prelaunch
```

Все revision ID сохранены. Три апрельских файла входят в поставляемую историю и обязательны вместе с изменённой майской миграцией. Нельзя переносить только изменение `down_revision` без этих файлов.

`web/migrations/versions/2026_05_01_1739-907b2d179318_.py` теперь продолжает апрельскую схему вместо повторного создания таблиц. Единственное различие baseline, SQL NULL в `audit_logs.details`, нормализуется в `{}` перед установкой NOT NULL. Остальные значения JSON остаются прежними. Downgrade до апрельской схемы возвращает nullable, но не превращает нормализованные `{}` обратно в NULL.

Базы с прежним stamp `907b2d179318` или более новой ревизией не выполняют этот шаг повторно. Тестовая копия исходной майской baseline сохранена без изменений в `web/tests/fixtures/migrations/may_2026_baseline.py`, вне пути поиска Alembic.

Шесть проверок в `web/tests/test_migration_history.py` включают:

- единственный base и head с сохранением revision ID;
- пустую схему, upgrade head, downgrade base и повторный upgrade;
- обновление с каждой из трёх апрельских ревизий с тестовыми аккаунтами, сессиями, подписками и токенами;
- сохранность аудит-записей, нормализацию SQL NULL и повторный upgrade без изменений данных;
- установку исходной майской baseline из сохранённого кода, stamp, upgrade head, downgrade до апреля и повторный upgrade.

Откат May → April сохраняет проверенные account/audit-данные. Это не обещание сохранности при произвольном downgrade: откат до base удаляет таблицы, а откат последующих функциональных миграций может удалять их данные, включая legal evidence. Проверка downgrade выполнялась только на disposable БД.

Каждый DB-кейс использует отдельную случайную схему внутри строго разрешённой disposable БД. Схема удаляется после теста; public не сбрасывается. Для production по-прежнему нужны резервная копия и проверка фактического stamp и схемы перед миграцией. Прямое редактирование `alembic_version` в production в эту работу не входит.

## Проверка точки запуска и доверия прокси

Новый `web/tests/test_legal_entrypoint.py` запускает настоящий Uvicorn с аргументами команды из Compose. Он использует localhost и отключает lifespan, поэтому не подключается к БД, Redis или брокеру. Тест проверяет default-deny, один доверенный прокси и цепочку доверенных адресов. Поддельные `Forwarded` и `X-Real-IP` не подменяют адрес клиента.

Это проверка точки запуска, не реального production-маршрута Traefik → nginx → web. Перед включением действующих документов необходимо проверить весь маршрут и указать только доверенные адреса прокси. Wildcard trust не используется.
