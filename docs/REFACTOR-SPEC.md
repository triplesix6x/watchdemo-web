# Спецификация аудита и рефакторинга watchdemo-web

Статус: пользователь утвердил весь план с gates (D24). Разрешена параллельная реализация независимых пакетов в изолированных worktree, затем production-рефакторинг после соответствующих baseline gates. Новые багфиксы, визуальные упрощения и production/небезопасные native-действия требуют отдельных решений. Общий scope включает также `D:/demo-manager`; полный журнал общих решений ведётся в `D:/demo-manager/docs/REFACTOR-SPEC.md`.

## Цель

Проверить архитектуру, структуру, расширяемость, сложность, лишнюю логику, мёртвый код и комментарии. Выполнить обоснованные структурные изменения после фиксации контрактов. Сохранить продуктовую логику, API, внешний вид, юридические документы, форматы, ошибки и значимые failure/concurrency-сценарии. Оптимизации допустимы без изменения результата и ухудшения внешнего вида.

Мобильный приоритет — плавность радара и анимации главной страницы. Сначала исследуется вся страница, затем вклад отдельных подсистем. Замена библиотеки, уменьшение DPR, частоты кадров, bloom, количества объектов, удаление стекла или idle-анимации не считаются автоматически эквивалентными оптимизациями.

## Согласованные условия

- Вопросы задаются по одному, с рекомендацией. Ответы, доступные из кода, устанавливаются исследованием.
- Полезная существующая работа сохраняется отдельным baseline-коммитом в основной ветке, затем создаётся отдельная локальная ветка рефакторинга. Итог закоммичен, дерево чистое. Push и deployment не разрешены.
- Найденные продуктовые баги согласовываются отдельно. Структурный перенос не должен скрыто менять ownership, retry, rollback, отмену или публикацию файлов.
- Существующие полезные QA-исходники, связанные исторические отчёты и PNG остаются на месте и могут войти в baseline-коммит. Новые детерминированные визуальные эталоны и метаданные окружения хранятся в Git. Новые traces, видео, профили и failed-run artifacts находятся вне репозитория и удаляются после разбора.
- Тестируются значимые контракты и сценарии каждого модуля, а не произвольные 100% строк. DTO, порты и ORM проверяются через соответствующие transport/use-case/conformance-сценарии, не пустыми тестами на каждый файл.
- Изменение модуля начинается после фиксации затрагиваемого поведения. Для UI нужны реальные mounted/DOM, interaction и визуальные проверки; source regex не заменяет их.
- Разрешены установка зависимостей и временный PostgreSQL/queue-стенд: loopback, фиктивные секреты, предварительная проверка fixtures, запрет реальной почты и Telegram. Временные данные удаляются.
- Проверки выполняются последовательно под Windows Job Object, на одном логическом CPU, с ограниченным timeout. Лёгкие проверки — 1024 MiB, тяжёлые — до 4096 MiB. Контейнеры и WSL не используются для обхода ограничений.
- Целевые мобильные браузеры — iOS Safari и Android Chrome. Физические телефоны пользователь проверяет после будущего выката; текущая задача выката не включает. Локальная эмуляция не считается проверкой Safari или физической плавности.
- Визуально незаметные упрощения графики допустимы только после сравнений и отдельного подтверждения пользователем неразличимости. Это не разрешение на мобильную версию с ухудшенной графикой.
- Параллельные писатели изолируются по worktree. Интеграция и общие файлы принадлежат основному агенту. Перед нетривиальными многофайловыми коммитами нужны независимые ревью корректности и качества текущего scope.

### Отдельно разрешённые исправления поведения

| Решение | Граница | Условие |
| --- | --- | --- |
| D17 | Атомарное потребление одноразовых auth-токенов | Сначала воспроизведение с двумя независимыми соединениями временной PostgreSQL. При подтверждении — отдельное исправление и коммит. Проверить обычный успех, повторное использование, срок действия, коды ошибок и rollback. Другие auth-политики не менять. |
| D18 | Безопасная публикация файлов релизов | Сначала воспроизведение повреждения/удаления при параллельной или прерванной загрузке на временных каталоге и БД. При подтверждении — отдельный коммит. Сохранить URL, формат, проверки и ответы обычных запросов. |

D16 относится только к desktop `wipe_all`. Другие web-дефекты пока не разрешены к исправлению. Изменение публикации API-порта, legal/quota-политик, UI-контраста, reduced-motion или analytics не входит в разрешения D17–D18.

D21: визуальный контроль строгий. Фиксируются среда, данные и моменты анимации. Допуск определяется шумом повторных baseline-снимков, не произвольным процентом. Стабильные отличия геометрии, цветов, текста и графики — регрессии. Упрощения требуют отдельного сравнения и подтверждения по D10.

D23: локальная оптимизация принимается сравнением до/после на одинаковых сценариях, среде и ресурсных ограничениях. Повторные замеры времени кадра и длинных кадров должны показывать воспроизводимое улучшение выше фонового шума, без функциональных и визуальных регрессий. Фиксированные мобильные 60 FPS и минимальный произвольный процент улучшения не обещаются. Если вмешательство не даёт доказанного выигрыша, оно не сохраняется под названием оптимизации.

## Безопасность проверки

Обычный frontend dev проксирует `/api` в production. Его нельзя использовать для сценариев с API без изоляции. Browser route interception не покрывает автоматически отдельный `context.request`.

До полного запуска требуется укрепить guards произвольного `TEST_DATABASE_URL`, crash collection, local-app QA origin, Focus/Ghost QA и output-каталоги. Неверный origin или DB target должен отклоняться до первого соединения. Существующие исторические PNG не перезаписываются новыми запусками.

Для режимов проверки нужны явные границы:

1. `pure`: без внешних соединений, fake settings.
2. `mock-browser`: настоящий UI, mock API, запрет внешних browser и request обращений.
3. `isolated-backend`: disposable сервисы по точному allowlist; не произвольный localhost и не production fallback.

## Открытые решения

- Утверждение конкретных структурных workpacks после сводки находок.
- Остальные отдельно согласуемые баги и security/deployment-вопросы.
- Конкретные моменты анимации и эмпирическая оценка GPU/font noise для строгого контроля D21.
- Конкретные workload и повторения для принятого сравнительного критерия D23.
- Полный dependency/license/security inventory и границы historical prototypes/assets.
- Конкретные финальные команды, доказательства по каждому модулю и статусы оставленных ограничений.

## Последовательность

1. Завершить интервью и сводку аудита; утвердить границы.
2. Сохранить проверенную полезную исходную работу отдельно от новых документов/исправлений.
3. Создать локальную ветку задачи.
4. Исправить безопасность proof infrastructure, затем зафиксировать исходные контракты и визуальные эталоны.
5. Параллельно реализовать утверждённые непересекающиеся пакеты в worktree; тяжёлые проверки запускать последовательно.
6. Отдельно воспроизвести и исправить D17/D18, не смешивая их с эквивалентными извлечениями.
7. Интегрировать последовательно, проверить реальный результат, сравнения и производительность, провести независимые ревью.
8. Закоммитить принятые изменения без push; удалить созданные временные файлы, проверить чистоту дерева и сохранность исторических материалов.
